在去年的时候，我把系统提示词比喻成需求文档。

[coze之系统提示词编写原则](https://mp.weixin.qq.com/s?__biz=MzIxODc1MTM2Nw==&mid=2247487910&idx=1&sn=3ade8174cbf9fea4bcf094a5486702e3&scene=21#wechat_redirect)

那编写需求文档，我们围绕三个点进行。

有什么，要什么，怎么做。

有什么，就是要提供对应的背景信息、角色、已有材料等。

要什么，就是明确目标、明确边界、明确成功标准。

怎么做，就是任务流程、执行顺序、验收方式。

![[00 临时箱/images/64f968a8b9e8f621f872234f3a789e0e_MD5.png]]

但后来我发现，很多时候我们明明把提示词写得很长，背景也交代了，要求也列了一堆。

_AI_ 最后交付出来的东西，还是不太对。

**不是完全不能用，而是总感觉差一口气**。

方向差一点，细节漏一点，结果和脑子里想的不是一回事。

这时候问题往往不在于一句话写得漂不漂亮，而在于我们没有把事情拆成一个能被执行、能被验证、能被纠偏的系统。

![[00 临时箱/images/2565846936b8947f2b7dbbcc90c0c3ac_MD5.gif]]

今年，在制作 _skill_ 的过程中，我又突然意识到一件事。

我们不管是利用 chatbot，还是 _agent_，去解决实际问题的时候，本质上都不是为了“对话”，而是为了把事情完成。

那目标越具体，边界越清晰，流程越规范，_agent_ 完成的效果就越好。

也就是说，

要知道怎么写提示词，其实就是在讲一套“如何成事”的方法论。

那如何成事？

本质就是要遵循客观规律，发挥主观能动性。

_AI_ 的能动性我们不用怀疑。

真正要被反复确认的，是客观规律有没有被讲清楚。

-   目标是不是清晰？
    
-   资源是不是可用？
    
-   边界是不是明确？
    
-   验收标准是不是具体？
    

所以我在想，与 AI 交互，完成目标。

不单单是写一套需求文档，而是写一套目标系统。

那就是 OCI 思维。

## 01 OCI 思维与 AI 交互

**OCI 本质上是以目标系统为核心的因果执行闭环**。

-   O - 目标：我要交付什么？成功的标准是什么？
    
-   C - 条件：我有哪些资源可以用？有哪些边界绝对不能碰？
    
-   I - 执行逻辑：如何动态地、自主地完成目标，并自我验证？
    

这仨加起来，本质上就是一个“如何成事”的框架。

O 决定方向。

C 决定条件。

I 决定过程。

![[00 临时箱/images/8f1248c7c52f40544c1e1c4cc26511db_MD5.png]]

如果只有 O，没有 C，模型可能知道你要什么，但不知道什么能用、什么不能碰。

如果只有 O 和 C，没有 I，模型可能知道目标和边界，但缺少推进、反馈、纠偏和验收。

**所以 OCI 不是把提示词写得更长，而是把目标系统写得更清楚**。

也就是说，它其实是在回答三个很朴素的问题：

-   终点在哪里？
    
-   手里有什么？
    
-   走偏了怎么回来？
    

C（条件）主要是两层：

边界：那些绝对不能突破的硬性约束。比如“不得编造事实”、“涉及付费必须停下确认”、“只能读取不能写入”。这些东西就像物理世界的客观规律，主观能动性必须在它的框架里发挥。

资源：我可以调用的工具、数据、模板。这些是构建因果链条的原材料。巧妇难为无米之炊，没有资源，什么也干不成。

在 C 中，需要符合客观规律。

比如：

错误的想法：

写“使用公司内部设计部提供的高清产品图”。

但模型根本拿不到这些图，那这句话就是一句正确的废话。

正确的写法：

“所有图片使用 picsum.photos 占位图服务，宽高比 4:3。”

这样模型立刻就能用。

在 C 中，也需要符合目标。

错误：

O 是制作极简个人站，但是在 C 里却要求“参考 Ant Design 的设计思想”，这就是把模型往沟里带。

正确：

“仅限纯 HTML/CSS/JS，严禁使用任何框架。”

这直接服务于“极简、无依赖”的目标。

在 I 中，需要有反馈机制。

尽管 agent 内部就有自我感知和修正系统，但是我们在与 agent 交互的时候，不管是直接让它完成目标，还是制作 _skill_，都要有系统循环思维。

也就是“观察→定向→决策→行动”的循环。

比如设置两个保护机制：一个是_熔断机制_，发现方向错了立刻停；一个是中断恢复机制，被打断后能从断点继续。

对于熔断和中断，我会在提示词中明确终止条件。

失败几次，就做个标记，继续下一个，或者触发终止条件。

如果条件不够，就停下来，提醒我补充缺少的资源。

![[00 临时箱/images/d3e512948ff9648e606615ba20acd045_MD5.png]]

## 02 不知道 C 怎么写

当自己也不清楚 C 的时候怎么办？

大部分时候，现有的目标已经够具体了，但还是不清晰。

还有一种情况是，我们知道自己要什么，但不知道 C 怎么写。

比如说，我想要搭一个学生作业交付网站，方便用户上传作业，也方便我对作业进行评分。

作为一个小白，我不知道：

-   好看的定义怎么评价？
    
-   技术栈应该怎么选？
    
-   用户画像是否清晰？
    
-   交互逻辑应该怎么样？
    

……

解决方法就是：

让模型通过提问来帮我明确需求。

这本身就是 I 执行逻辑的第一个标准步骤。

比如，在提示词里这样设计：

你的首要任务不是直接动手，而是先通过提问，跟我一起明确需求。每次只问 1-2 个最关键的问题。对技术选型类问题，给我 2-3 个选项，并说明优劣。在所有关键决策点明确之前，禁止写任何代码。

这样，模型就从“被动执行者”变成了“需求引导者”。

![[00 临时箱/images/d1818ab27801d5802c43e7ae6806b407_MD5.gif]]

它不是等我把所有条件都想清楚，而是在对话中帮我把模糊的需求一步步变清晰。

## 03 先把 O 写成可验收结果

OCI 里最容易被忽略的，其实是 O。

很多人以为自己已经写了目标。

比如：

帮我做一个好看的个人网站。

这当然是目标，但不是一个可执行、可验收的目标。

因为“好看”太模糊，“个人网站”也太宽泛。

模型可以做一个黑金风，也可以做一个极简风；可以做作品集，也可以做博客首页；可以只做一个页面，也可以做完整站点。

这些都叫“个人网站”，但交付出来可能完全不是你想要的东西。

所以 O 要写成可验收的交付清单。

比如：

交付一个极简个人作品集网站，包含首页、关于我、项目作品、技能、联系表单、页脚。项目作品不少于 4 个卡片，联系表单包含姓名、邮箱、留言 3 个字段。页面需要在 375px 和 1440px 宽度下正常显示。

这样就不一样了。

模型知道要交付什么，也知道什么情况算完成。

**我理解的 O，不是“愿望”，而是“结果”**。

不是“帮我优化一下”，而是“优化到什么程度算通过”。

不是“写得高级一点”，而是“读者看完能理解什么、能拿走什么、能直接怎么用”。

![[00 临时箱/images/ab6d75a59b99cea5808094aaf726b8b7_MD5.png]]

## 04 定性定量拆解思维

AI 时代，学会对世界的具体表达，尤为关键。

把所有模糊概念都拆成可以具体识别、可以判断的指标。

这就要用到定性定量思维。

定性，是明确方向。

比如“要语义化”、“要响应式”、“要有高级感”、“要适合公众号阅读”。

定量，是划定尺度。

比如“项目卡片不少于 4 个”、“联系表单有 3 个字段”、“首屏不超过 2 屏”、“小标题控制在 15 个字以内”。

比如说，我们在 skill 编写中，会加验收标准。

这也是 C 的一个重要环节，边界判断。

有一种方法就是把语言的定性，写成类似 SOP 的判断项。

比如，把 I 的验收标准写成打分卡时，判断就不再是“感觉还行”，而是逐项打勾：

· 项目卡片不少于 4 个？是 / 否

· 表单有 3 个字段？是 / 否

· 代码中无框架语法？是 / 否

· CSS 包含 @media 查询？是 / 否

全部通过，才算完成。

没有商量的余地，也没有模棱两可的“差不多”。

定量的话，我会给它一个赋分标准。

比如说对于信息图，不同的评分，可能会走向不同作图方式。

可以设置一个关键指标，比如信息密度：

0-3 分，低密度。

4-6 分，中密度。

7-9 分，高密度。

让 AI 自行打分，再选择路由方向。

指标的确定，对于 OCI 思维，还有 skill 稳不稳定，都是一个关键环节。

![[00 临时箱/images/15ab1aac0b0d794d232e3a30d0ad4dba_MD5.gif]]

## 05 大目标拆小目标

大目标由多个小目标串联而成，要学会拆解思维。

当面对一个复杂目标时，比如“做一套完整的公众号排版 skills”，不要试图用一个 O 去覆盖所有东西。

要把它拆成多个子 OCI 单元：

| 项目 | 说明 |
| --- | --- |
| O₁ | 标题的确定 |
| O₂ | 内容排版的规范 |
| O₃ | 公众号发布流程 |

每个子任务有自己的 O、C、I，可以独立开发、独立测试。

最后再设计一个总控系统，负责分派任务、管理依赖、仲裁冲突、最终验收。

更重要的是，拆 O 的时候，C 和 I 也必须同步拆。

如果我只是把大目标切成几块，但每块的 C 和 I 还是笼统的，那这个拆解就是换汤不换药。

底下的人，或者模型，拿到手还是不会干活。

比如说我的排版skills中，有设置一个总控skill。

![[00 临时箱/images/e47a6deee6f3a36e95ab6fffc7a42ab4_MD5.png]]

## 06 用 OCI 思维的重要性

没有 OCI 思维的人，写提示词，上来就是在"许愿"。

![[00 临时箱/images/3bef6c564e75a9c89d29753bc2a7ee45_MD5.png]]

有 OCI 思维的人，写提示词，上来就是思考系统。

在执行的时候，会多想一层。

不是一上来就让 AI 干活，而是先把任务过一遍。

比如说，现在要让 AI 帮我们做一件完整的事。

它可以是写一篇公众号文章，可以是做一张信息图，可以是做一套 PPT，也可以是搭一个个人作品集网站。

表面上看，这些任务不一样。

但真正执行的时候，其实都逃不开同一套问题。

第一步：需求澄清

可以让 AI 问你，也可以自己思考，再问 AI 推荐。

我要交付的是文章、海报、PPT、网页，还是一个可运行的工具？

发布在哪里？

公众号、小红书、朋友圈、官网，还是内部汇报？

谁来看？

小白用户、技术读者、老板、客户，还是学生？

使用的是什么 agent 工具？

集成的 coze？百度秒哒？trae 等 IDE 工具？_codex_？claude？

要做应用？

是要做网站？做 App？做客户端？

如果要做网站，

选纯 HTML/CSS/JS？React？Vue？还是全栈 Next.js？

如果你不知道怎么选，或者完全小白，可以让 AI 给你推荐。

直到所有关键决策点都确认了，才进入下一步。

这里我们继续拿个人作品集网站举例。

第二步：定义 O（可验收的交付清单）

| 项目 | 说明 |
| --- | --- |
| 三个文件 | index.html、style.css、script.js |
| 六大板块 | 导航、关于我、项目作品（至少 4 个卡片）、技能（6-8 项）、联系表单（3 个字段）、页脚 |
| 视觉 | 暗色主题，系统默认字体栈 |
| 功能 | 导航固定并支持平滑滚动 |
| 响应式 | 375px 和 1440px 宽度下正常显示 |
| 素材 | 所有图片用占位图服务 |

第三步：定义 C（资源与边界）

资源：

· 技术栈：纯 HTML5、CSS3、原生 JS。图标用 Font Awesome CDN

· 图片：picsum.photos 占位图

规范：

· 三文件分离，无内联样式

· 使用语义化标签，CSS 用 BEM 命名

· CSS 文件开头有目录注释

禁区：

· 严禁使用任何框架

· 联系表单提交地址用占位符，并注释说明

第四步：定义 I（执行与验收流程）

| 项目 | 说明 |
| --- | --- |
| 规划 | 先输出文件结构图，自检所有板块是否都在 |
| 构建 | 依次生成 HTML、CSS、JS。每生成一个，对照 C 的规范和 O 的清单自查 |
| 验收 | 交付前逐项打勾，全部通过才能交付 |

最终交付的提示词长这样：

【O｜目标 - 交付物规格】

交付一个极简个人作品集网站模板，三个文件：index.html、style.css、script.js。

内容包含导航、关于我、项目作品（至少 4 个卡片）、技能、联系表单、页脚。暗色主题，响应式设计，所有图片使用占位图。

【C｜条件 - 资源与规范】

仅限纯 HTML5、CSS3、原生 JS。严禁使用任何框架。三文件分离，无内联样式。图标用 Font Awesome CDN。CSS 使用 BEM 命名，开头有目录注释。

【I｜执行与验收流程】

  
-   先输出文件结构图，自检板块是否齐全
    
  
-   依次生成 HTML、CSS、JS，每生成一个对照规范和清单自查
    
  
-   最终验收逐项打勾：板块齐全、卡片 ≥ 4、表单 3 字段、无框架语法、有响应式查询
    
  
-   全部通过后交付
    

所以，OCI 可以被压缩成一个通用模板：

【O｜目标】

我要交付什么？成功标准是什么？什么结果算完成？

【C｜条件】

我有哪些资源可以用？有哪些限制？哪些事情绝对不能做？

【I｜执行闭环】

先做什么？如何自检？什么情况下继续？什么情况下停下来问我？

这个模板不复杂，也不是绝对的，主要在于引导我们的思考。

但是它能让模型从“听指令”，变成“围绕目标做事”。

![[00 临时箱/images/15ab1aac0b0d794d232e3a30d0ad4dba_MD5.gif]]

## 07 最后的话

OpenAI 的 GPT-5.6 Model guidance 里也提到：

> GPT-5.6 能更好地从上下文里推断用户的底层目标和预期工作量，所以很多时候不需要把每一步都规定死。

但同时，仍然要提供领域背景、硬约束、审批边界和成功标准。

你该做的不是规定步骤，而是定义目标、约束和标准，然后把执行路径交给模型自己选。

这也印证了我的思考。

**提示词设计的真正方向，不是写出更长的指令，而是构建更精确的系统**。

**提示词不只是写需求文档，而是设计目标系统**。

不管是我们设计 skill 也好，设计 _MCP_ 也好。

它的本质就是研究如何定义一个目标，然后构建一个系统，让事情必然能够做成。

![[00 临时箱/images/3fce84a4105edefd6f2a6f73e2369bb7_MD5.png]]

当我悟到，与 agent 交互，需要目标思维时。

我在想用哪个词归纳这一思考的时候，于是就想到了 OCI。

当然，OCI 思维并不是把目标、条件、执行都写死。

得看任务类型，给予模型发挥的灵活度。

对于确定性任务，

比如制作网页，控制权拉满，C 和 I 精确量化。

对于创意性任务，

比如爆款文章，O 依然要具体，但 C 提供的是“火种”（优秀案例作为审美标尺），I 可以适当交出控制权，相信模型能通过案例自行领悟。

所以我理解，普通提示词更多是在描述要求。

OCI 思维，是先把事情放进一个目标系统里，再让模型在系统里发挥能动性。

不是把所有步骤都写死。

而是把目标、条件、反馈机制交代清楚。

**这样模型发挥能动性的时候，不是在瞎猜，而是在边界里推进**。

目标定义得越清楚，模型就越不需要猜。

![[00 临时箱/images/7170bd57d5ee0d3bd01a22abb5e36cb4_MD5.gif]]

**边界给得越明确，它犯错的空间就越小**。

闭环设计得越完整，事情就越接近“必然能做成”。

OCI 模型为我们与大模型的交互提供了一套可推导、可验证、可迭代的方法论。

它的终点，不是一份优秀的提示词，而是一个持续逼近“必然成事”的执行系统。
