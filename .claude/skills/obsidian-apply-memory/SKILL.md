# obsidian-apply-memory

## 核心定位

第二大脑管线的**第三步**：执行真正的"长期记忆生长"——把用户确认过的内容，从 `memory/inbox/` 合并进 people / projects / wiki / decisions / daily。

**这是唯一会写长期目录的技能，因此必须谨慎：先出计划，拿到用户明确确认，再动手。**

## 关键原则：确认门（Confirmation Gate）

合并是**两阶段**的，绝不一步到位：

1. **第一阶段 — 出计划**：分析待合并内容，生成一份「合并计划」（`occ-merge-plan` 代码块，见 Step 3），呈现给用户。**到此停止，等待用户操作。**
2. **第二阶段 — 执行**：两条路径——用户在审核卡片上**勾选合并**（插件直接写入，你不动手）；或用户**以文字明确确认**（如"确认 / 合并吧 / 合并前两条"，无卡片环境的兜底），此时才由你按计划写入。

如果用户只是模糊回应或没确认，**不要写入**，再次澄清要合并哪些。

## 触发条件

- 用户已审核 inbox（可能用过 review-inbox），现在说"合并 / 确认沉淀 / apply"。
- 用户指定了要合并的具体条目。

## 必读（按顺序）

1. `profile.md`、`vault.md`、`memory_policy.md` —— 基准与规则。
2. `memory/inbox/` 相关文件（含 `_review-*.md` 审核清单，若有）。
3. **目标长期文件的现有内容**（合并前必须先读，避免重复 / 冲突 / 覆盖）。

## 步骤

### Step 1：确定待合并集合
- 若用户指定了条目 → 只处理这些。
- 若用户说"全部" → 以最近的 `_review-*.md` 清单为准。
- 拿不准就先问清楚，别擅自扩大范围。

### Step 2：读目标文件现状 + 矛盾检测
对每个目标（如 `people/张三.md`），先读已有内容，决定是**追加新小节**还是**新建文件**。

**矛盾检测（必做）**：逐条对照待合并内容与目标文件（以及明显相关的其他长期文件），找出三类问题：
- **直接矛盾**：新内容与旧记忆说法相反（如旧记"偏好 A 方案"、新记"已放弃 A 改用 B"）。
- **过时覆盖**：新内容表明旧记忆已失效（职位变了、项目结项了、结论被推翻了）。
- **重复**：同一事实换了说法再次出现。

矛盾**不能静默合并**：必须在合并计划的"⚠️ 冲突"区逐条列出——各引用两边原文、给出你建议的处理（保留新的并把旧的标注"已过时（YYYY-MM）"/两者并存并注明分歧/放弃新条目），由用户裁决。没有矛盾时明确写"未发现与既有记忆的矛盾"。

> 为什么这是必做项：没有一致性维护的记忆库会从资产腐烂成负债——两条互相矛盾的记忆同时存在时，未来的每次召回都可能给出错误答案。

### Step 3：生成合并计划（呈现，不写入）

先用一两句话总结本次合并的范围，然后输出一个 `occ-merge-plan` 代码块——**桌面对话面板会把它渲染成可勾选的审核卡片**，用户逐条勾选后由插件直接写入（逐字节等于你给出的 content）：

````md
本次共 3 条候选，1 条与既有记忆冲突（默认不勾选，由你裁决）：

```occ-merge-plan
{
  "v": 1,
  "title": "合并 2026-07-14 的候选记忆",
  "items": [
    {
      "target": "people/张三.md",
      "op": "append",
      "content": "## 近期动态（2026-07-16）\n- 转岗负责支付方向（来源：[[2026-07-14]] 会议记录）",
      "summary": "新增近期动态：转岗做支付",
      "source": "memory/inbox/2026-07-14.md"
    },
    {
      "target": "projects/第二大脑.md",
      "op": "create",
      "content": "# 第二大脑\n\n## 定位\n- …",
      "summary": "新建项目档案",
      "source": "memory/inbox/2026-07-14.md",
      "conflict": "与 wiki/工具选型.md 2025-11 的结论矛盾：当时记录'不再自建'。建议保留新结论并把旧条目标注'已过时（2026-07）'。"
    }
  ]
}
```

确认方式：直接在上方卡片勾选后点「合并选中项」；或回复文字告诉我合并哪几条。
````

**字段规则（必须严格遵守）：**
- `v` 固定为 `1`；`items` 是数组，每条一个写入动作。
- `target`：**工作区相对路径**，必须在长期记忆目录（people/ projects/ wiki/ decisions/ daily/ palace/）内且以 `.md` 结尾。其他目标会被插件判定"超出合并范围"而不可勾选。
- `op`：`append`（目标已存在，追加到末尾）或 `create`（新建文件）。先读目标现状再决定。
- `content`：**最终逐字写入的 Markdown**——不是摘要。要包含小节标题、日期、来源标注、`[[双链]]`；主观推断标 "Agent 判断"。插件不会改写一个字，所以这里必须是成品。
- `summary`：一句话说明这条是什么（卡片行展示）。
- `source`：该条来自的 inbox 文件（工作区相对路径）。插件合并后会自动在该文件末尾标注 `✅ 已合并 → <target>`。
- `conflict`：**矛盾检测（Step 2）发现问题时必填**——引用两边原文、给出建议处理。有 conflict 的条目在卡片上默认不勾选，由用户裁决。没有矛盾就省略该字段，并在代码块外注明"未发现与既有记忆的矛盾"。

输出代码块后**到此停止**。不要自己执行写入——用户勾选后由插件完成。

### Step 4：执行（仅当用户以文字确认时）

- **卡片路径（默认）**：用户在审核卡片上勾选并点「合并选中项」→ 插件直接写入并标注 inbox，**你无需也不应再执行任何写入**。下一条消息的【系统备注】会告诉你合并结果。
- **文字路径（兜底，如微信端等无卡片环境）**：用户以文字明确确认（"确认 / 合并吧 / 合并前两条"）→ 按原流程亲自写入：严格按计划、追加优先不覆盖、保留 `[[双链]]` 与来源标注、主观推断标 "Agent 判断"，并执行 Step 5 的 inbox 回写。

### Step 5：回写 inbox 状态（仅文字路径需要你做）

文字路径合并完成后，在对应 inbox 条目后标注 `✅ 已合并 → <目标文件>`（追加标注，不删除原文），让 inbox 有迹可循。卡片路径下插件已自动完成。

## 输出

- 第一阶段：简短导语 + `occ-merge-plan` 代码块（桌面端渲染为审核卡片；不落盘）。
- 第二阶段：卡片路径由插件写入；文字路径由你按计划写入 people/ projects/ wiki/ decisions/ daily/，并在 inbox 标注已合并。
- 结束时总结：合并了几条、落到哪些文件、还有哪些留待下次（卡片路径下此总结由系统备注驱动，收到备注后简要确认即可）。

## 禁区

- ❌ **未经用户明确确认（卡片勾选或文字确认），绝不写长期目录。**
- ❌ 用户已通过卡片合并的条目，不要再重复写入。
- ❌ 不覆盖长期文件既有内容（只追加 / 新建）。
- ❌ 不删除 inbox 原始记录（只追加"已合并"标注）。
- ❌ 不改动 raw/。
- ❌ 不把推测当事实。
