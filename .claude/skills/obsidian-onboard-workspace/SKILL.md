# obsidian-onboard-workspace

## 核心定位

这是用户第一次"让第二大脑认识我"。但**方式不是访谈**——访谈逼用户从零描述自己，填进去的是"我希望成为的样子"，还颠倒了权威（你刚进我的库，就审问我？）。

正确方式是**发现式**：Agent 先读用户的库（索引鸟瞰 + 几篇代表性笔记深读），然后告诉用户"**我看到的你**"——身份、工作对象、常见产出、写作风格、该记什么不该记什么。**每条都标出依据**。用户来纠正、补充（这个纠正环节就是轻访谈，用户会把未来意图、明确偏好丢出来），**明确确认后才落盘**。

读库读不到的部分（未来意图、明确禁令）由用户的补充带进来；库是空的，就走诚实重定向。绝不 5 连问，绝不套职业模板。

## 触发条件

- 用户点击"让我认识你 / 完成基础设置"。
- 用户说"帮我建档 / 让你了解我 / onboarding / 读读我的库然后告诉我你看到的我"。
- `profile.md`、`work_mode.md`、`style.md`、`memory_policy.md` 仍是模板状态或明显空白。

## 必读（按顺序）

1. `.obsidian-cc/recall-service.json` —— 读取 port/token 后调用本地 `GET /overview?k=200`，获得已经过 KnowledgeMap 实时过滤的全库鸟瞰（`g` gist、`t` 标题、`tg` 标签、`h` 小标题、`m` mtime）。服务缺失或 entries 为空 → 走 Step 1b 空库兜底。
2. **代表性笔记原文**：从 overview 里挑 3–6 个 Vault 相对路径 `p`，逐个调用 `GET /read?p=...`，阅读返回的 `content` 验证和丰富归纳。不要直接读取 `vault-index.jsonl` 或旧版 `a` 绝对路径。
3. `.obsidian-cc/knowledge-map.md`（存在则说明是原地接入模式）。
4. 原地模式读取 `.obsidian-cc/context/` 下四个画像文件；legacy 模式读取根目录同名文件。已有内容只追加/增量，不覆盖。
5. `vault.md` —— legacy 目录约定（缺失就跳过）。

> 调用本地服务统一使用 `curl -s -G "http://127.0.0.1:<port>/<endpoint>" -H "Authorization: Bearer <token>" --data-urlencode ...`。不要把 token 发往任何非回环地址。

## 步骤

### Step 1 · 读库认识你

- 根据 overview 元数据归纳出**有依据的观察**：
  - 用户像在**做什么领域 / 角色**（从标题、标签、gist 的高频主题反推）。
  - 反复出现的**人物 / 项目 / 主题**（可继续用安全召回服务搜索专有名词）。
  - **写作风格**：语气（简洁/啰嗦/学术）、结构（要点/叙述/表格）、长度。
  - **库的组织方式**：哪些目录在用、笔记密度、有没有双链习惯。
- 选 3–6 篇代表性笔记，通过安全 `/read` 读取，验证归纳、补细节。
- 每条观察都要能指向依据（"来自你 12 篇关于 X 的笔记"）。归纳不出来的，就老实说"这部分我读不出来"。

### Step 1b · 空库兜底（仅当索引缺失 / 库为空）

诚实说，不要装：

> 你的库还是空的（或我还没读），我没法从笔记里认识你。两个选择：
> (a) 你用一两句话告诉我：你是谁、主要在做什么、常见产出是什么——我据此起草。
> (b) 先写几篇笔记、让我读一遍（`重新读库`），再来。
>
> 我不会用 5 个问题审问你，也不会把你套进某个职业模板。

走 (a) 时，**最多问 1–2 个开放问题**，让用户自然语言回答，不要求格式。

### Step 2 · 提议草稿（呈现，不写）

基于 Step 1，起草四份文件的**增量**内容。原地接入模式写入 `.obsidian-cc/context/`，legacy 模式写入根目录同名文件：

- `profile.md`：身份、当前重心、正在做的事、沟通偏好。
- `work_mode.md`：工作对象、产出、驾驶舱关注维度、信息路由偏好、节奏。
- `style.md`：语气、结构、长度、格式偏好。
- `memory_policy.md`：值得沉淀 / 不沉淀 / reports、sources、inbox 的边界（多数情况下模板已够用，按用户领域微调即可）。

**关键纪律**：
- 推断一律标 `(Agent 判断)`，并给依据；区分"笔记里真读到的"和"我猜的"。
- 明确向用户要**读不出来的那部分**："我读到了你的领域和风格，但读不出你**接下来的重心**、**明确不想要的偏好**——这些你补一下。"（这就是轻访谈的入口，把残留的 20% 收进来。）

把草稿铺在对话里，然后停下等回应。

### Step 3 · 等用户纠正 / 确认

明确问：

> 哪里不对？哪里漏了？如果没问题，回复"确认写入"，我再落盘。

用户**没有明确确认前**，不要写文件。用户纠正的内容（尤其是新增的未来意图、明确偏好）要并入草稿。

### Step 4 · 确认后写入（走确认门）

用户明确确认后，用 Write / Edit 更新四个文件。**每次写入都会被结构化确认门拦截**（插件级 canUseTool），用户逐条点头才落盘。已有内容只追加/增量，不覆盖。

写完后，建议用户通过问库或“帮我看看这篇”验证画像是否真正改善了知识复用；学习工作流包启用时才建议 `/obsidian-feynman`。

## 输出

- 草稿清单（对话内）。
- 经确认的四文件增量更新。
- 结束总结：从库里读出了什么、用户补充了什么、哪些文件改了、还有哪些待补。

## 禁区

- ❌ **不读库前不编身份 / 职业 / 工作对象。** 推断必须有依据、标 `(Agent 判断)`。
- ❌ **未经用户明确确认，不写** `profile.md`、`work_mode.md`、`style.md`、`memory_policy.md`。
- ❌ 不搞 5 连问；不套职业模板、不建职业专用目录。
- ❌ 不覆盖四文件既有内容（只追加 / 增量）。
- ❌ 不把 onboarding 草稿写入 `memory/inbox/`。
- ❌ 不改动 `raw/`。
