# 技术公众号与博客写作

这个 Skill 只用于技术公众号、博客和需要讲清系统机制的长文。产品介绍、功能巡礼、更新日志、普通推广文案不应套用它。

## 开始前先拿到足够证据

1. 明确读者、读者亲身经历过的痛点、文章能带来的具体改变，以及全文必须回答的一个原理层问题。
2. 使用 search_vault 找到真实项目记录、排查过程、数据和既有表达，再用 read_note 核对原文。只有用户明确提供或当前上下文能够读取的仓库代码，才可以作为真实代码引用。
3. 缺少代码、日志、时间戳、版本或实验输出时，明确告诉用户缺什么并索取材料。不能编造经历、数字、代码、测试结果或情绪。
4. 如果无法访问代码仓库或运行实验，就把这项限制写清楚，不要把推测伪装成验证结果。

## 内容必须同时有人味和干货

文章必须回答为什么这样设计、不这样会坏在哪里、机制如何运转。只罗列做了什么的功能清单、特性巡礼和更新日志不成稿。

技术叙述按这条顺序推进：先给现象或动机，再讲裸方案会出什么问题，然后沿真实时间线或调用链讲机制与代码，最后主动交代边界情况、脆弱点和还没做的事。跳过问题，读者就不知道这个设计买到了什么；跳过边界，文章会显得在装完美。

主线叙事优先于分点罗列。讲运行时或系统时，沿一个请求、一个回合或一次故障排查的真实过程向前走，让结构从内容里长出来。架构图式的一二三四五只适合做概览，不能代替文章主线。

代码必须来自实际仓库或可运行实验，并注明文件路径、版本或提交来源。只截取解释机制所需的关键行，省略处用注释标明。每段代码前说明它要解决什么，代码后解释关键行怎样改变系统行为，不能裸扔代码。

数字必须具体且可复现，包括时间戳、分布、行数、版本和测试步骤。不确定的信息明确标为不确定。承认脆弱与未完成是可信度来源。

## 开头先回答这跟读者有什么关系

第一段从读者亲身经历过的痛点场景开场，例如你有没有遇到一个长任务切到后台就没了。紧接着说明文章能带来的三到四项具体收益，可以使用加粗短项。读完前三段，读者应能回答这跟自己有什么关系。

不要使用宏大背景式开头，例如在 AI 飞速发展的今天。也不要从评论同行文章开始。背景和技术动机放进第一个小节，不占开头版面。

至少放入一个真实演示，而且要靠前。能运行就展示真实命令、输出、时间戳或报错，例如 kill -9 后重新启动并核对日志。证据本身比形容词更有说服力。

每讲完一个机制，马上说明使用者能感知到什么变化。例如进程可以被系统回收，但会话还能从已完成工具结果继续，因此用户才敢把长任务交给它。机制是原因，获得感是结果，两者缺一不可。

## 小标题要推动叙事

小标题要少而准确，可以口语化，但只看目录就应知道每一节讲什么。可以写先说没有运行时会怎么死，或者那么，我们来看一个完整回合是怎么跑的。

禁止文艺式、悬念式和比喻式标题。旅程、真相、之道、那些事这类词通常没有交代章节内容。小 bug、边角修复和次要动机并进相关段落，不单独成节。只有承载独立原理或机制的内容才配独立章节。

小标题之间应当形成推进关系，而非并列的能力目录。每节结尾不写换一种说法的总结句；需要承上启下时，只用一句话引出下一节要解决的问题。

## 句子要完整，也要有呼吸

以完整书面句为主体。正常陈述句可以带一两个从句，二十到五十字是健康区间。连续三个以上的超短句说明逻辑没有组织好，应把因果关系接回句子，而不是靠断句制造节奏。

逗号按密度管理，不按个数管理。中文书面句带四五个逗号很正常；一句超过五个逗号，或平均每十二个字就有一个逗号时，再拆句或改写。为减少逗号而把句子拆碎，伤害更大。分号在一句里最多一个，一段超过两个分号就重写。

口语化意味着语气松弛，不意味着句子破碎。可以在完整句中少量使用得承认、说白了、图省事、当时没想太多，每千字两三处即可。

破折号整篇最多一个，默认不用。补充说明优先使用逗号、括号或另起完整句。冒号只用于引出代码、列表或结论，不承担修辞功能。

每段二到五句，只讲一件事。单句成段只用作重音，一篇最多两三次。不是 A，而是 B 的句式整篇最多一次；对仗式金句最多一个，靠近结尾；不用排比句。

## 引号只在确有引用时出现

引号只用于三种场合：报错或日志原文、别人说过的话、真正的文件名或标识符。不要给普通概念和口头语加引号，也不要靠引号强调。

全文引号不超过三对。超过时逐一检查，大多数概念去掉引号后含义不会损失。需要强调概念时用加粗，或者把定义写成完整句。

## 图只负责全景，文字负责为什么

文章讲流程、时序或架构时，准备一张时序图、流程图或泳道图。图片应适合约 750 像素宽的手机正文区，文字不小于 11 像素等效尺寸，主色不超过两种，深色只用于最重要元素。每张图配一句图注，直接告诉读者应该看什么。

优先交付可保存到 docs 目录的 SVG。如果当前 Agent 没有创建任意 SVG 文件的工具，就给出明确的制图内容和可复制的 SVG 源码，或者说明需要用户补充这一步；不能声称文件已经生成。图只替代概览性描述，不能替代原理解释。

表格只用于真正的对照场景，例如黑名单和配置项。不要用表格做能力清单或总结矩阵。

## 保留真实的排查和决策过程

写出第一反应猜了什么、查看什么证据后改了主意、在哪一步卡住了多久。直奔正确答案的叙事容易像事后编造。已经确认的错误要讲清当时为什么会那样写，依赖网页结构等脆弱设计也要主动说明风险。

使用具体锚点，例如几点几分、第几行、多长间隔和报错原文。犹疑必须对应真实的不确定性，可以少量使用大概、可能、我猜；证据足够后也要收口，明确说明这条判断是否成立。

情绪只能写真实发生过的，一次一处，一句话以内。编造的激动比没有情绪更糟。

## 禁用空话

以下词语默认删除，除非它们在具体技术语义中不可替代：

| 类别 | 禁用词 | 处理方式 |
| --- | --- | --- |
| 互联网黑话 | 赋能、抓手、闭环、范式、颗粒度、对齐（非技术义） | 删除 |
| 空洞形容词 | 强大、优雅、完美、显著、精妙、高效、丝滑 | 换成具体事实或删除 |
| 空洞副词 | 非常、极其、深度、全面、高度 | 删除 |
| 总结腔 | 本质上、归根结底、总的来说、综上所述、不言而喻 | 删除 |
| 假共鸣 | 值得我们深思、不难发现、众所周知 | 删除 |
| 口号腔 | 让我们一起、未来已来、拭目以待、必将成为 | 删除 |
| 自我评价 | 很棒的、最值的、精心的 | 删除，好坏交给读者 |

删掉形容词后信息量没有下降，说明它只是装饰。用可观察事实替换它。

## 发布前逐条自查

交稿前必须完成下面的检查，发现不通过就直接修改，不要只把检查结果列给用户：

1. 价值：第一段是不是读者自己的痛点，前三段能否回答这跟我有什么关系，全文有没有说明这项机制改变了用户的什么工作。
2. 证据：是否至少有一个真实演示，真实代码是否注明来源，数字是否可复现，无法验证的部分是否明确说明。
3. 原理：有没有至少一个不这样设计会坏在哪里的论证，是否讲清机制，而非罗列功能。
4. 结构：有没有章节复述前文，小标题是否形成推进，只看标题能否预知各章内容，边角问题是否误占独立章节。
5. 朗读：随机朗读三段，修复碎句、断掉的因果和结巴处。
6. 标点：破折号是否不超过一个，单句逗号是否超过五个或密度过高，一段是否出现两个以上分号。
7. 修辞：排比、对仗、不是而是和金句是否超额。
8. 引号：全文是否不超过三对，并且只用于日志、引语和真实标识符。
9. 图：涉及流程时是否有一张手机可读的图，图注是否告诉读者看什么。
10. 结尾：最后一段是否停在具体事实，例如还欠什么、代码或资料在哪里、哪些地方欢迎核验。抒情、升华、喊话和空泛展望全部删除。

## 修改时优先把是什么改成为什么必须如此

弱写法只说联网解析、HTML 转文本一共一百行，这仍然是小功能介绍。更有价值的写法会指出执行可以并发，但工具结果必须按模型发起调用的顺序写入日志；如果按完成顺序提交，同一段代码在不同设备上就会产生不同的对话历史，日志重放无法复现。

弱写法会把一次故障拆成许多短句，只营造紧张感。更可信的写法会保留真实调用次数、时间戳、线程状态、出错函数和具体字节位置，把现象、证据和原因组织在一个完整段落中。

交付文章时，同时列出仍缺少的真实材料和没有验证的边界。用户确认需要沉淀后，再用 create_knowledge_candidate 创建待审核文章，不能绕过审核直接写入 Vault。
