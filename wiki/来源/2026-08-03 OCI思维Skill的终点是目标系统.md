# OCI思维：Skill的终点是目标系统

> 原文：[[00 临时箱/OCI思维：Skill的终点，不是指令，而是目标系统]]
> 作者：小爽爽鸭
> 来源：微信公众号「小爽爽学智能体鸭」
> 发布时间：2026-08-03

## 核心观点

**提示词设计的真正方向，不是写出更长的指令，而是构建更精确的系统**。

**提示词不只是写需求文档，而是设计目标系统**。

与 Agent 交互，完成目标，本质不是"对话"，而是**把事情做成**。

## 问题根源

明明把提示词写得很长，背景也交代了，要求也列了一堆，但 AI 交付的东西还是不对。

**不是完全不能用，而是总感觉差一口气**。

问题不在于一句话写得漂不漂亮，而在于**没有把事情拆成一个能被执行、能被验证、能被纠偏的系统**。

## OCI 思维框架

### 定义

**OCI 本质上是以目标系统为核心的因果执行闭环**。

- **O - 目标**（Objective）：我要交付什么？成功的标准是什么？
- **C - 条件**（Condition）：我有哪些资源可以用？有哪些边界绝对不能碰？
- **I - 执行逻辑**（Implementation）：如何动态地、自主地完成目标，并自我验证？

### 三者关系

- O 决定**方向**
- C 决定**条件**
- I 决定**过程**

如果只有 O，没有 C：模型知道你要什么，但不知道什么能用、什么不能碰。

如果只有 O 和 C，没有 I：模型知道目标和边界，但缺少推进、反馈、纠偏和验收。

**OCI 不是把提示词写得更长，而是把目标系统写得更清楚**。

### 回答三个问题

- 终点在哪里？
- 手里有什么？
- 走偏了怎么回来？

## C（条件）的两层含义

### 1. 边界

那些绝对不能突破的硬性约束。

- "不得编造事实"
- "涉及付费必须停下确认"
- "只能读取不能写入"

这些就像物理世界的客观规律，主观能动性必须在它的框架里发挥。

### 2. 资源

可以调用的工具、数据、模板。

这些是构建因果链条的原材料。**巧妇难为无米之炊，没有资源，什么也干不成**。

### C 需要符合客观规律

❌ 错误：写"使用公司内部设计部提供的高清产品图"
- 但模型根本拿不到这些图，这是正确的废话

✅ 正确："所有图片使用 picsum.photos 占位图服务，宽高比 4:3。"
- 模型立刻就能用

### C 需要符合目标

❌ 错误：O 是制作极简个人站，但 C 里却要求"参考 Ant Design 的设计思想"
- 把模型往沟里带

✅ 正确："仅限纯 HTML/CSS/JS，严禁使用任何框架。"
- 直接服务于"极简、无依赖"的目标

## I（执行逻辑）需要反馈机制

尽管 agent 内部有自我感知和修正系统，但在与 agent 交互时，都要有**系统循环思维**。

### OODA 循环

"观察→定向→决策→行动"的循环。

### 两个保护机制

1. **熔断机制**：发现方向错了立刻停
2. **中断恢复机制**：被打断后能从断点继续

### 在提示词中明确

- 失败几次，就做个标记，继续下一个，或触发终止条件
- 如果条件不够，就停下来，提醒我补充缺少的资源

## 不知道 C 怎么写？

### 问题

目标已经够具体了，但还是不清晰。知道自己要什么，但不知道 C 怎么写。

**案例**：想搭一个学生作业交付网站，但不知道：
- 好看的定义怎么评价？
- 技术栈应该怎么选？
- 用户画像是否清晰？
- 交互逻辑应该怎么样？

### 解决方法

**让模型通过提问来帮我明确需求**。

这本身就是 I 执行逻辑的第一个标准步骤。

在提示词里设计：

```
你的首要任务不是直接动手，而是先通过提问，跟我一起明确需求。
每次只问 1-2 个最关键的问题。
对技术选型类问题，给我 2-3 个选项，并说明优劣。
在所有关键决策点明确之前，禁止写任何代码。
```

模型从"被动执行者"变成了"需求引导者"。

不是等我把所有条件都想清楚，而是在对话中帮我把模糊的需求一步步变清晰。

## O（目标）要写成可验收结果

### 问题

很多人以为自己已经写了目标。

❌ "帮我做一个好看的个人网站。"

这是目标，但不是**可执行、可验收的目标**。

"好看"太模糊，"个人网站"也太宽泛。

### 正确写法

✅ 交付一个极简个人作品集网站，包含首页、关于我、项目作品、技能、联系表单、页脚。项目作品不少于 4 个卡片，联系表单包含姓名、邮箱、留言 3 个字段。页面需要在 375px 和 1440px 宽度下正常显示。

模型知道要交付什么，也知道什么情况算完成。

### O 的理解

**不是"愿望"，而是"结果"**。

- 不是"帮我优化一下"，而是"优化到什么程度算通过"
- 不是"写得高级一点"，而是"读者看完能理解什么、能拿走什么、能直接怎么用"

## 定性定量拆解思维

AI 时代，学会对世界的具体表达尤为关键。

**把所有模糊概念都拆成可以具体识别、可以判断的指标**。

### 定性：明确方向

- "要语义化"
- "要响应式"
- "要有高级感"
- "要适合公众号阅读"

### 定量：划定尺度

- "项目卡片不少于 4 个"
- "联系表单有 3 个字段"
- "首屏不超过 2 屏"
- "小标题控制在 15 个字以内"

### 验收标准打分卡

把语言的定性写成类似 SOP 的判断项：

- 项目卡片不少于 4 个？是 / 否
- 表单有 3 个字段？是 / 否
- 代码中无框架语法？是 / 否
- CSS 包含 @media 查询？是 / 否

全部通过，才算完成。没有商量余地，也没有"差不多"。

### 定量赋分标准

信息图案例，根据信息密度：

- 0-3 分：低密度
- 4-6 分：中密度
- 7-9 分：高密度

让 AI 自行打分，再选择路由方向。

## 大目标拆小目标

### 拆解原则

当面对复杂目标时，不要试图用一个 O 去覆盖所有东西。

**把它拆成多个子 OCI 单元**。

### 案例：公众号排版 skills

| 项目 | 说明 |
|------|------|
| O₁ | 标题的确定 |
| O₂ | 内容排版的规范 |
| O₃ | 公众号发布流程 |

每个子任务有自己的 O、C、I，可以独立开发、独立测试。

### 关键

**拆 O 的时候，C 和 I 也必须同步拆**。

如果只是把大目标切成几块，但每块的 C 和 I 还是笼统的，那这个拆解就是换汤不换药。

### 总控系统

设计一个总控系统，负责：
- 分派任务
- 管理依赖
- 仲裁冲突
- 最终验收

## 完整执行流程案例

### 任务：制作个人作品集网站

#### 第一步：需求澄清

- 交付物是什么？（文章、海报、PPT、网页、工具？）
- 发布在哪里？（公众号、小红书、朋友圈、官网？）
- 谁来看？（小白用户、技术读者、老板、客户？）
- 使用什么 agent 工具？（coze、百度秒哒、trae、codex、claude？）
- 技术选型？（纯 HTML/CSS/JS？React？Vue？Next.js？）

如果不知道怎么选，让 AI 推荐。

#### 第二步：定义 O（可验收的交付清单）

| 项目 | 说明 |
|------|------|
| 三个文件 | index.html、style.css、script.js |
| 六大板块 | 导航、关于我、项目作品（≥4卡片）、技能（6-8项）、联系表单（3字段）、页脚 |
| 视觉 | 暗色主题，系统默认字体栈 |
| 功能 | 导航固定并支持平滑滚动 |
| 响应式 | 375px 和 1440px 宽度下正常显示 |
| 素材 | 所有图片用占位图服务 |

#### 第三步：定义 C（资源与边界）

**资源**：
- 技术栈：纯 HTML5、CSS3、原生 JS
- 图标：Font Awesome CDN
- 图片：picsum.photos 占位图

**规范**：
- 三文件分离，无内联样式
- 使用语义化标签，CSS 用 BEM 命名
- CSS 文件开头有目录注释

**禁区**：
- 严禁使用任何框架
- 联系表单提交地址用占位符，并注释说明

#### 第四步：定义 I（执行与验收流程）

| 项目 | 说明 |
|------|------|
| 规划 | 先输出文件结构图，自检所有板块是否都在 |
| 构建 | 依次生成 HTML、CSS、JS。每生成一个，对照 C 的规范和 O 的清单自查 |
| 验收 | 交付前逐项打勾，全部通过才能交付 |

### 最终提示词模板

```
【O｜目标 - 交付物规格】
交付一个极简个人作品集网站模板，三个文件：index.html、style.css、script.js。
内容包含导航、关于我、项目作品（至少 4 个卡片）、技能、联系表单、页脚。
暗色主题，响应式设计，所有图片使用占位图。

【C｜条件 - 资源与规范】
仅限纯 HTML5、CSS3、原生 JS。严禁使用任何框架。
三文件分离，无内联样式。图标用 Font Awesome CDN。
CSS 使用 BEM 命名，开头有目录注释。

【I｜执行与验收流程】
- 先输出文件结构图，自检板块是否齐全
- 依次生成 HTML、CSS、JS，每生成一个对照规范和清单自查
- 最终验收逐项打勾：板块齐全、卡片 ≥ 4、表单 3 字段、无框架语法、有响应式查询
- 全部通过后交付
```

## OCI 通用模板

```
【O｜目标】
我要交付什么？成功标准是什么？什么结果算完成？

【C｜条件】
我有哪些资源可以用？有哪些限制？哪些事情绝对不能做？

【I｜执行闭环】
先做什么？如何自检？什么情况下继续？什么情况下停下来问我？
```

这个模板主要在于引导思考。

能让模型从"听指令"，变成"围绕目标做事"。

## OpenAI GPT-5.6 Model guidance 印证

> GPT-5.6 能更好地从上下文里推断用户的底层目标和预期工作量，所以很多时候不需要把每一步都规定死。

但同时，仍然要提供：
- 领域背景
- 硬约束
- 审批边界
- 成功标准

**该做的不是规定步骤，而是定义目标、约束和标准，然后把执行路径交给模型自己选**。

## 任务类型与灵活度

### 确定性任务

比如制作网页，控制权拉满，C 和 I 精确量化。

### 创意性任务

比如爆款文章：
- O 依然要具体
- C 提供的是"火种"（优秀案例作为审美标尺）
- I 可以适当交出控制权，相信模型能通过案例自行领悟

## 核心理解

### 普通提示词 vs OCI 思维

**普通提示词**：更多是在描述要求

**OCI 思维**：先把事情放进一个目标系统里，再让模型在系统里发挥能动性

### 不是写死步骤

而是把目标、条件、反馈机制交代清楚。

这样模型发挥能动性的时候，**不是在瞎猜，而是在边界里推进**。

- 目标定义得越清楚，模型就越不需要猜
- 边界给得越明确，它犯错的空间就越小
- 闭环设计得越完整，事情就越接近"必然能做成"

## 终点

OCI 模型提供了一套**可推导、可验证、可迭代**的方法论。

它的终点，不是一份优秀的提示词，而是一个持续逼近**"必然成事"**的执行系统。
